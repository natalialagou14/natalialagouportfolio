System

One library, four atomic levels, and a token under every value a screen can set.

Figma library 4 atomic levels Tokenised foundations Mobile + desktop

Objective

Give the BOX merchant app one source for every element it is built from, so that a change made once arrives everywhere — across both surfaces and every screen in the product.

The system has two halves. Underneath sits a tokenised layer: typography, spacing, corner radii and element dimensions, each named for what it is for rather than what it measures. On top of it sits a component library structured by Atomic Design — atoms, molecules, organisms and pages — hosted centrally so every product draws from the same shelf.

Why the library carries the weight

  • The same component appears on a phone in a kitchen and on a counter screen in the same shop. A single definition with responsive rules is the only way both stay true to each other.
  • Colour in BOX is load-bearing, not decorative. The fulfilment channel is stated in one coloured word, and that colour then has to survive the banner, the list badge, the progress stepper and the time picker — four different components that only agree because the library says so.
  • A component is not finished when it is drawn once. It is finished when the library also shows it disabled, mid-transition, and carrying a state sentence long enough to wrap — which is what stops each screen inventing those states differently.
  • There is one designer and several developers. The library is what lets a component be updated once and reviewed once, instead of found and fixed screen by screen.

Context

BOX is a Greek food delivery platform. Its admin tool serves four distinct roles — Back Office agents, Content agents, Merchants, and Wave admins — and the merchant-facing app runs both on a phone and as a desktop app on the counter.

This library is the shared foundation under all of it: built in Figma, hosted as a centralised library, and structured so a component carries its own themes and its own contextual scenarios rather than leaving them to whoever places it.

Typography tokens

To maintain uniform text hierarchy throughout BOX, I established a comprehensive system of typography tokens. Each token defines a clear use case — covering titles, body copy, captions, and button labels — while establishing hierarchy through primary, secondary, and emphasised text styles. Responsive definitions were created to ensure fluid visual consistency.

Naming a token for its use case rather than its size is the part that does the work: a title stays a title when the scale moves, and a caption cannot quietly become body copy because someone liked it bigger on one screen.

Layout tokens

A matching tokenised structure was implemented across all other spatial and layout properties, including spacing, corner radii, and element dimensions.

Token layer What it defines Why it is a token
Typography Titles, body copy, captions, button labels — each in primary, secondary and emphasised Hierarchy stays readable when the scale changes
Spacing Gaps between elements, and padding inside them Rhythm survives a component being reused somewhere denser
Corner radii The radius of every surface that has one Radius signals what kind of object something is
Dimensions Element heights, widths and tap targets A control stays reachable one-handed on both surfaces

Read the last column: every layer exists because something breaks without it when the same component is placed on a second surface, by a second person.

Implementation & structure

The BOX Merchant app was built in Figma following Atomic Design principles — structuring elements into atoms, molecules, organisms, and pages for mobile and desktop screens. All UI assets are hosted in a centralised library to maintain seamless consistency across the application.

The fourth level, pages, is where mobile and desktop finally differ. Everything below it is shared, which is why the same order can open as a full screen on a phone and as a modal on the counter without either being drawn twice.

The three channel colours

The clearest thing the library buys is a colour that means the same thing in every component it touches. BOX has three fulfilment channels, and each one owns a hue that follows the order through the whole app.

Each hue is defined as a pair — a full-strength value for type and rules, and a tinted background for banners and badges. The brand action colour is deliberately kept out of this set: the channel colour tells a shop which kind of order it is answering, the button colour tells it that it is answering one. Those two jobs never share a hue.

Biggest challenge

Deciding where a component stops. Pushed too far down, everything becomes an atom and the library turns into a parts bin nobody can assemble from. Pushed too far up, every screen becomes its own organism and the system stops saving anyone anything.

The line that worked was to let the surface decide: anything that is identical on a phone and on the counter lives at organism level or below and is drawn once; anything the two surfaces genuinely disagree about is deferred to the page level. That rule is why an order card and a sheet could be shared while the order screen itself is a full screen on mobile and a modal on desktop.

Expected impact

  • Rapid component updates. A change lands in one place and reaches every screen carrying it.
  • Brand flexibility. Because the palette and the type scale are tokens, a retheme is a token change rather than a redraw.
  • A unified experience across touchpoints. Mobile, responsive and desktop products draw from the same shelf, so they read as one product.
  • Shorter handoff. A component that arrives with its states and its dimensions attached leaves far less to be asked about later.
